# Changelog

All notable changes to Lobster will be documented in this file.

## Unreleased

- A `null` written in a list matches a missing field, as `== null` does: `$a.json.v in [null, ""]` (and `[null] contains $a.json.v`) did not hold when `v` was missing.
- `lobster graph` prefixes every Mermaid node (`s_end`), so a step named `end`, `style`, `class`, `graph` or another Mermaid keyword no longer makes a graph Mermaid refuses.
- A response schema that cannot be used (`ask --schema` with a bad `$ref`, a command's `requestInput`) says why, as a workflow `input:` step and `llm.invoke` already did.
- A malformed `LOBSTER_LLM_ADAPTER_URL` or `LOBSTER_PI_LLM_ADAPTER_URL` is reported as `Invalid URL` before the call, as a malformed `OPENCLAW_URL` is (it read "request failed: Invalid URL").
- `runs advance` of a run whose `for_each`, `parallel`, `repeat` or `switch` failed on its own (its timeout, a `repeat` out of rounds, a `switch` with no matching case) runs that step as its next attempt: the commands inside got the same `LOBSTER_ACTIVITY_ID` and `LOBSTER_ACTIVITY_ATTEMPT` as the first time, so a host deduplicating on them skipped the re-run.
- A run blocked because a command was interrupted says the same thing however it is reported (when it stopped, and when `runs advance` meets it again): its outcome is unknown, `lobster runs abandon` stops it, and `runs advance` runs it again only if the step has `recovery: repeat` (not said for standalone pipelines and SDK runs, which have none). It told every run to continue with `runs advance` (an SDK run with `Lobster.advance`), which only blocked it again, with a message that named the step differently and left out abandoning.
- `runWorkflowFile`, `advanceWorkflowRun` and `abandonWorkflowRun` refuse a `leaseMs` under 100 before opening the store, as `advanceDueRuns` and `signalEvent` do: they opened (or created) the state directory first, and said "Workflow run not found" for an unknown run.
- A run that stopped on something a retry would meet again (a pipeline asking for approval or input where the run cannot pause, such as in a child workflow, or a `cost_limit` with `action: stop` already spent) has no step for `runs advance` to retry: it says to start the run again. It ran the step's commands, and made its model calls, again each time, only to stop the same way.
- A step whose `when:` fails at run time (comparing a string with `>`) fails as any step does: its `on_error` applies, and `runs advance` retries it. The run failed past `on_error: continue`, and `runs advance` said no step had failed.
- Resuming a token whose pause an older Lobster saved asks for `lobster upgrade` from core's `runWorkflowFile` and the SDK's `Lobster.resume` too, not only from the tool runtime (they said the resume state was not found).
- `lobster history prune` and the store handle's `retain` read only the finished runs old enough to remove: they read every run in full, with its attempts, events and saved outputs.
- A command's flag given together with its alias (`approve --limit 2 --preview-limit 3`, `ask --subject-from-stdin --subjectFromStdin`), a string or number flag given no value (`approve --prompt --limit 2` asked "true"), and a number flag without a number (`approve --limit abc`), are refused with the pipeline's other flag errors, before any stage runs (a `parse_error`): one spelling was used and the other ignored, each command preferring a different one, and a bad number fell back to a default.
- A run's cost (`_meta.cost`, `cost_limit`) counts model calls as `llm.invoke` makes them, under the step that made it (the `workflow:` step for a call in a child workflow, `loop.step` inside a loop). A cached or replayed answer is never counted, however later steps pass it on, because it is not a call. Usage that other commands print is no longer counted: it was read from step output, and keeping a call counted exactly once that way took marks saved with the run, a ledger of open charges and a list of billed calls, which a long series of fixes kept finding gaps in. Calls of every branch of a `parallel` step count, a `wait: any` race's losers too, and so do calls whose step later failed. A pause saved by an older version keeps its recorded spend, without the charges it had left open.
- An approval that fails at the terminal (a refused approver, a read that timed out) fails only the question: `runs advance` asks it again without running the step's command again (it said no step had failed).
- `lobster run --mode tool` reports a cancelled run as `cancelled` (it said `ok`).
- A relative `cwd:` (on a step, a workflow, a child workflow or a loop) is the run's directory's, as a step without `cwd` already ran there: resuming or advancing from another directory, or a tool host passing `ctx.cwd`, no longer looks for it under the caller's directory.
- The SDK's `exec(cmd, { cwd })` resolves a relative `cwd` the same way.
- Core `runWorkflowFile` reads a relative `filePath` from the run's directory (`ctx.cwd`), as `runToolRequest` does.
- A host's `onExecutionStarted` hook fires once before a shell step's command and once per pipeline dispatch: it also fired for steps that run no command (an approval alone), and twice for a pipeline step.
- A missing working directory is no longer reported as a missing shell or command.
- A run converted from an older version, which saved no directory, runs in the directory of whoever continues it, a tool host's `ctx.cwd` included, as before the upgrade.
- Removed the `trackRuns` option (`openStoreSession`, `PersistenceOptions`, `new Lobster`, the store handle) and the `LOBSTER_RUNS` variable: every run is recorded, so they changed nothing.
- A run started from inside a step (a command or SDK stage calling `runToolRequest` or `runWorkflowFile` with its own `ctx.env`) is a run of its own: it took over the step's run, and was refused or reported that run's ID.
- Core `signalEvent` refuses a non-string event name before storing it. Core `runWorkflowFile` refuses a decision (`approved`, `response`, `cancel`) without `resume`, and `args` or `definition` with one (the other half was dropped; a resumed run keeps its own definition). Core `resumeToolRequest` refuses more than one decision before any store work, for a token or approval ID as for a wait ID. A dry run (`ctx.dryRun`) is refused by `advanceWorkflowRun`, `abandonWorkflowRun`, `signalEvent` and by `runWorkflowFile` when resuming or running a definition (it ran the steps for real, or crashed); `advanceDueRuns` treats it as its own `dryRun`.
- `lobster signal --id` and core `signalEvent` refuse a delivery ID that is blank, not a string, or over 256 characters (an empty ID made every later delivery with it a silent duplicate).
- Core `signalEvent` refuses a `leaseMs` under 100 before it stores the event (the event was stored and every run it woke failed), and `advanceDueRuns` refuses a bad `leaseMs` or `limit` up front (a negative `limit` advanced every due run).
- An invalid `callerId` (empty, or over 256 characters), or a `leaseMs` under 100, is refused before a run is written: it left a run that was never due and never pruned, and, converting an older SDK token, used the token up.
- An SDK host scoped by `callerId` can resume a token from an older SDK: the run it becomes belongs to that caller (it was created unscoped, so the caller who converted it could not see it, and the token was used up).
- Core `resumeToolRequest` and `getWait` refuse a malformed request (a bad wait ID or token, conflicting references) before opening the store, so a refusal no longer creates the state directory and database; a malformed wait ID is a `parse_error`. `exec --shell` refuses words after its command line, and a bare `--shell` without one (both ran less than was typed). `exec` also refuses a bare or empty `--stdin` (it dropped the input). A flag value outside the flag's declared choices (`exec --stdin bogus`, or `--stdin JSON`: the formats are lowercase) is refused before any stage runs, so the stages before it no longer act first. A dry run leaves a value built from step output (`--stdin $fmt.stdout`) to the run. Core `runToolRequest` and `lobster run` check a request (a pipeline that does not parse, or names an unknown command or flag, included: now a `parse_error`, exit 2) before they create a run, so a refusal writes nothing and does not depend on the store. `lobster graph` exits 2 for a workflow file that does not exist, as `lobster run` does. `lobster run --dry-run` on a workflow file refuses a pipeline step's unknown flag, as the run does. `runs advance` and `runs abandon` refuse a malformed run ID before opening the store, as `runs show` does. `history show` reports a run it cannot find (exit 1) and refuses a malformed run ID, and `history list` a malformed cursor, as `runs show` and `runs list` do (they printed `null`). An approval ID must be 8 lowercase hex characters: `resume --id` and core `resumeToolRequest` refuse anything else with a `parse_error` (other characters were stripped, so a mistyped ID could answer a different approval). Core exports the typed `runPipeline` the SDK exports (it exported the runtime's untyped one). A resume no longer takes the state-key file lock to read its question (questions are store transitions), so a held lock on a stored value cannot hold it up. A wait ID is any `<run id>.<64 hex>`, as the store makes them (`lobster resume` read some as tokens). The dry-run plan labels a `parallel` step's own timeout `branches timeout`, apart from the step's `timeout_ms`. Core `runToolRequest` refuses `args` that are not an object, or `args` with a pipeline, with a `parse_error` as the CLI does (they were misread or dropped). `lobster graph` refuses words it would not use. The SDK's `resumeWait` refuses a malformed wait ID or revision before opening the store, throwing as `resume` does for a malformed token.
- Execution history records each activity under its activation key (`root/a/attempt-1/activity`); the paths had an empty segment (`attempt-1//activity`). A pipeline step's stages are recorded under its activity (`root/a/attempt-1/activity/pipeline/0`; they were under `root/a/attempt-1/step/a/pipeline/0`). The SDK's `advance` names no run in a failure for a run it could not claim (an unknown ID, or another caller's run), as `lobster runs advance` does.
- `lobster resume <waitId>` without `--expected-revision` reports a wait that was already answered as `wait_conflict`, as it does with one (it was a `runtime_error`). The SDK's `resumeWait` returns a failed result for a failure that is not a refusal (an invalid `callerId`, a store that cannot open), as `run` does; it threw.
- An answer by wait ID that loses a race to another answer is a `wait_conflict` (the SDK's `resumeWait` throws `WaitConflictError`), as one refused before the race is; depending on timing it was a `runtime_error` ("Resume state not found").
- Core `resumeToolRequest` always returns an envelope: a cancellation or rejection its host stopped was thrown or returned depending on when the stop landed.
- An answer of the wrong kind says what the question needs for every caller (`approved` or `response`, and the CLI flag), instead of only the CLI flag.
- A failed `lobster runs advance <runId>` or `lobster resume` names the run in its envelope (`runId`), as `lobster run --mode tool` does.
- `runs advance --due` and `signal` report a run whose advance was stopped (Ctrl-C, a lost lease) with its saved status, `waiting` or `running`, not `failed`.
- A pipeline dry run in tool mode returns the same envelope as any successful run (`requiresApproval` and `requiresInput` were missing).
- `lobster run --mode` refuses a value other than `human` or `tool` (a misspelled `tool` ran in human mode).
- `lobster run` refuses what its target would not use: `--args-json` with a pipeline (quote the pipeline to give a command its own `--args-json`), and pipeline words after `--file` (both were dropped and the run went ahead).
- `lobster runs advance` reads `--due` as a flag (`--due false` advanced every due run, `--due=true` was refused), and refuses `--limit`, `--concurrency` and `--dry-run` without it.
- In human mode, `lobster run` names a run that ends in an error (`Run <runId>: ...`), so it can be looked at with `runs show` and continued.
- A run refused for being, or not being, an SDK run is refused before it is created.
- A `lobster run --mode tool` that fails before it starts (a pipeline or `--args-json` that does not parse) no longer names a run ID: that run was never kept.
- `lobster run <workflow file>` records its run as kind `workflow`, as tool mode and the SDK do (it said `cli`).
- A pipeline that emits an input request where steps cannot pause (a parallel branch, a child workflow) now says why, as an approval there does.
- A `switch` step's `env` and `cwd` apply to the steps of its case, as they do inside `repeat`, `for_each` and `parallel` (they were ignored). A failed `lobster runs advance <runId>` reports `{ ok: false, error }` like every other tool-mode failure (it also sent `status: "error"` and empty result fields). The `lobster upgrade` report counts converted pauses as paused runs (workflows and pipelines) and lists paused SDK steps among the imported items; when it only moves files an interrupted upgrade had already imported, it says where instead of "Nothing to upgrade".
- A workflow file is refused when `stdin` is set on a step that never reads it (`workflow`, `parallel`, `for_each`, `repeat`, `switch`, `sleep`, `wait`), or `workflow_args` on a step that is not a `workflow` step: both were silently ignored, so a child workflow or a parallel step got no input. Core exports `RunToolOptions`, the options of `runToolRequest`.
- Steps that `on_error: skip_rest` leaves unrun inside a switch case or a repeat, and the losing branches of a `parallel` race, are recorded as skipped (`$id.skipped` is true), as a switch's other cases are; so are the steps inside a switch, repeat or parallel step whose failure `on_error` tolerates: a later step reading them failed with "Unknown step reference".
- A workflow file's pipeline steps (nested steps, parallel branches and the child workflows it names included) are checked before any step runs: a misspelled command or flag in a later step failed the run only after earlier steps had acted. A command name or flag value holding a step reference (`$id.path`, an input answer included) is checked once the run fills it in.
- A step or parallel branch whose `run`, `command` or `pipeline` is only blanks is refused when the workflow loads (it requires a command); it used to load and then do nothing. A blank `pipeline` beside a `run` is ignored, as the run already ignored it.
- A workflow file's `args` are checked when it loads: each name maps to an object with only `default` and `description` (a string). A misspelled `defualt` or a bare value used to load and then leave `${name}` unresolved.
- `cost_limit.max_usd` must be a number. A string such as `"0.5"`, or an empty value, used to load; reaching the limit then failed the step with a TypeError, which `retry` and `on_error` handled as a step failure, so `action: stop` did not stop the run.
- Retrying a failed run asks a pipeline step's approvals and questions again when the step runs again: the answers given before the failure were kept and applied to items the person never saw.
- Resuming a token for a run another caller owns is refused like an unknown token (`ResumeRefusedError`, which the SDK throws); it was reported as a failed result.
- A workflow file's `name` and `description` must be strings.
- In a run, a pipeline's `approve`, `ask` or `requestInput` answered at a terminal is asked by the engine, as a step's `approval:` is: the prompt is shown on the terminal (in a workflow file's `pipeline:` step it went into the step's output, replacing its items), a "no" cancels the run (it failed the step, which `retry` re-ran and `on_error: continue` let through), and the time a person takes does not count against the step's timeouts.
- An answer typed at the terminal that does not parse or fit its question stops the run, as the same answer sent with `resume` is refused: a step's `retry` no longer re-runs the step (and the pipeline stages before the question) for a person's typo, and `on_error: continue` no longer goes on as though the question had been answered. `runs advance` asks the question again. A pipeline's `ask`, asked in a run, takes a typed answer as text again (`approve` for `{ "decision": "approve" }`), as it does outside a run; `input:` steps and `requestInput` still take JSON.
- An approval answered at the terminal takes `y`/`yes` or `n`/`no` (any case; an empty line is the `N` the prompt offers), as `resume --approve` does. Any other answer, such as `ys` or `yeah`, fails only the question and `runs advance` asks again; it used to count as a "no" and cancel the run for good.
- `ask` and `requestInput` asked at a terminal by the one-shot `runPipeline` wait only `LOBSTER_APPROVAL_INPUT_TIMEOUT_MS`, as `approve` does; they waited for good. Core's `parsePipeline` takes the same `CommandLookup` registry as `runPipeline`.
- A setting given under two names is refused, not half dropped: a step or parallel branch with both `run` and `command` (only `run` ran), and an approval with an identity setting in both spellings (`required_approver` and `requiredApprover`, and likewise for `initiated_by` and `require_different_approver`; only the camelCase one was read), in a workflow file or in a step's output asking for approval.
- A step nested anywhere inside a `for_each` body (a switch case, a repeat, an inner loop) may not take the name of a step before the loop or of a loop variable in scope (`item_var`, `index_var`, an outer loop's too): it hid that name, so later steps read the shadowing step's output instead.
- A pause saved by an older Lobster inside a pipeline stage (`requestInput`, in a pipeline or a workflow's pipeline step) is refused when its pipeline has no such stage, before the answer is used up; it used to be converted and then fail.
- `lobster graph` draws the reads of steps inside a `repeat`, a parallel step or a `for_each` body: an edge from such a step that a later step reads starts at its `repeat` or parallel step, and what the steps inside read (`stdin`, conditions, `until`) is drawn into that step. It drew neither.
- A pipeline that asks (`ask`, `approve`, `requestInput`) where steps cannot pause (a parallel branch, a child workflow, a retried loop or switch, a `for_each` with `concurrency`) stops the run, saying why, in tool mode too. In tool mode it failed the step with "requestInput is not supported in this pipeline context", which `retry` re-ran and `on_error: continue` let through.
- A gated step (`approval:`, `input:`, `sleep:`, `wait:`) refused where steps cannot pause, such as inside a child workflow, stops the run as a pipeline's refused question does: a parent's `retry` ran the whole child again only to be refused again, and its `on_error: continue` hid the refusal.
- A step's output that asks for approval (`{ prompt, requiredApprover, ... }`) can no longer replace the approval rules of the workflow or the host: the step's `approval:` settings and the `LOBSTER_APPROVAL_*` variables win, and the output only fills in what they leave unset. A command printing `requiredApprover: mallory` let mallory approve a step whose file required alice.
- No step inside a `switch` case or a `repeat` may take the id of the step around it: it replaced the step's own result (`$s.case` was lost).
- The host's approver rules (`LOBSTER_APPROVAL_REQUIRED_APPROVER`, `LOBSTER_APPROVAL_REQUIRE_DIFFERENT_APPROVER`, `LOBSTER_APPROVAL_INITIATED_BY`) apply to an `approve` inside a pipeline, as to a step approval: anyone could approve it. The variables are now documented.
- `--dry-run` of a workflow file checks what a start checks: the child workflows it names load, and their pipeline steps name known commands and flags. It reported a plan for a workflow that would be refused before its first step.
- A parallel branch named `approval` (or `activity`) no longer stands in for its step's own gate: a `parallel` step with `approval:` whose branch had that id completed without asking anyone, with the branch's output as the step's. A branch's history path now reads `<step>/attempt-1/branches/<branch>`.
- A standalone pipeline's messages do not name a workflow step called `pipeline`: a refused approver says "Approval requires approver ...", an input request too large for the envelope "Input needs_input envelope exceeds ...", and a pipeline that halted "Pipeline halted before completion ...", as an invalid input already did.
- A child workflow's commands see only the args it takes: the parent's `LOBSTER_ARG_*` variables reached them, though `LOBSTER_ARGS_JSON` listed only the child's.
- `lobster history show` lists the waits a run published and answered (its `waits` was always empty for a workflow run), and `LOBSTER_APPROVAL_INPUT_TIMEOUT_MS` and `LOBSTER_MAX_TOOL_ENVELOPE_BYTES` are documented.
- A misspelled key or flag is matched to the nearest known one: `whn` on a step suggested `run`, the first name within two edits, rather than `when`.
- Input, workflow args, or a stage's output or question that a run cannot save (a function, a BigInt) is refused before the run is created, or fails the step: it left the run `running` for good, as every later save failed, with nothing able to advance, abandon or prune it.
- Another caller's approval ID is refused exactly like an unknown one, so a caller cannot tell that someone else has a question pending under it.
- Step output shaped like Lobster's saved-record reference (`{"$lobster.record": ...}`) comes back as it was after a pause; it was read as a reference, so the resume failed or another saved value took its place.
- A resumed or retried run puts its large saved outputs back before it saves anything: the save that records an answer (or a retry) wrote each output's reference as a new record, and a run stopped right after it handed later steps the reference instead of the output.
- A pause converted from an older version is written as every checkpoint is: an old step output shaped like a saved-record reference no longer left a run that could not be advanced or abandoned.
- Core's `runWorkflowFile`, `advanceWorkflowRun`, `abandonWorkflowRun`, `advanceDueRuns` and `signalEvent` take the same context as `runToolRequest` (a `ToolRunContext`, with its defaults filled in): given only `{ storeSession }` or `{ env }`, as the reference shows, they failed to type-check, and at run time a later pipeline step found no command registry. `ToolRunContext` takes `hooks` (`RunHooks`, now exported), and core's `WorkflowRunOptions` no longer shows the engine's own fields (`definition`, `kind`, `sdk`).
- A pause converted from an older version resumes though today's parser reads its flags differently (`--json=true`): resuming compares the paused pipeline's stages by their text and runs them as parsed now; it failed with "workflow pipeline changed since input request".
- A misspelled `recovery` names its step or branch, and a bad `retentionDays` option is reported under its own name rather than `LOBSTER_RUN_RETENTION_DAYS`.
- `lobster upgrade` skips a paused workflow whose saved pipeline stages lack their text, as it does for a paused pipeline; it converted it, and the resume then failed. A paused pipeline now saves only its stages' text, which is all a resume compares.
- A workflow that declares `args:` refuses an arg it does not take (with the nearest name it does) and a declared arg with no default that is not given, for the workflow run and for each child it names, before any step runs: either left `${name}` empty in its commands. A workflow without `args:` takes any args as before.
- A store handle's `listRuns` checks its filter as core's `listRuns` does (an unknown status or an empty caller ID is refused; it returned an empty page), and finding an approval's ID reads only approval entries from the store.
- A workflow file is refused when a `stdin`, `for_each`, branch `stdin` or `wait.match` value is a step reference (`$id.path`) to a step that does not run before it, as a condition with one is: it failed only once the steps before it had acted.
- A workflow file is refused when `env` is not an object of strings or `cwd` is not a string, on the workflow, a step or a parallel branch: an unquoted `PORT: 8080` was dropped without a word, and `cwd: 5` failed only once the run had started. A NUL in an `env` name or value is refused too.
- A workflow file is refused when `env` or `cwd` is set on a step that runs no command and contains no steps (`sleep`, `wait`, `input`, an approval alone): they were dropped.
- A workflow file is refused when a step sets both `when` and `condition` (only `when` was read, so a `condition` meant to skip the step was dropped), or a `for_each` sets `batch_size` without `pause_ms` (it only says how many items run between pauses).
- Deliberate waits that do not pause the run (a question answered at the terminal, a `pause_ms` between batches, a `sleep` short enough to wait in place, a retry delay) no longer count against the `timeout_ms` or `heartbeat_timeout_ms` of the steps around them, as a pause never did. A `switch` with `timeout_ms: 1000` around a `sleep: 2s` timed out, while the same sleep taken as a pause (`LOBSTER_INLINE_SLEEP_MS=0`) did not; a loop with a heartbeat limit was stopped as hung during its own `pause_ms`. A crash or a stop during such a wait gives those steps a fresh budget, as it does during a pause. Inside a `parallel` step or a `for_each` with `concurrency`, a wait in one branch does not hold the step's clocks, since the other branches are still working.
- A bad answer typed at the terminal to a pipeline's question (`ask --emit`: JSON that does not parse or fit the schema) fails only the question, as a failed approval does: `runs advance` asks again without running the pipeline's earlier commands again (it ran them twice). A `wait:` step that pauses inside a step with `timeout_ms` (a loop, a switch) saves that step's cleared deadline: the event arriving after the timeout no longer fails the step with "Step timeout expired during interruption". A step that retries forgets what its failed attempt left: a run stopped while a timed-out loop waits to retry stays due, instead of blocked on a command that was no longer running.
- The SDK's one-shot `runPipeline` has typed options (`RunPipelineOptions`: parsed stages, a command lookup, streams, env) and a typed result (`RunPipelineResult`, items as `unknown[]`); it took and returned `any`. When `runs advance` refuses to rerun a step that may have acted, it no longer suggests `runs abandon` (which leaves a failed run as it is): the run stays failed.
- `resumeToolRequest` refuses a token and an approval ID together (`parse_error`); it used to check one and answer the other. A token from a version that kept workflow state inside the token now gets the same message from the SDK as from the CLI.
- A step's progress (`LOBSTER_HEARTBEAT_FILE`, `ctx.heartbeat()`) also counts for the steps around it: a `for_each` with `heartbeat_timeout_ms` no longer stops a step inside it that beats against its own, shorter limit.
- An answer that makes more than one decision (say `approved` and `cancel` together, from JavaScript) is refused with a `parse_error` and the run keeps waiting; it used to cancel the run. `InvalidAnswerError` and `ResumeRefusedError` are exported from the SDK and the core, so hosts can tell a refused resume or a bad answer apart; the SDK throws `InvalidAnswerError` for an answer with no or several decisions. A run's `status` in `getRun` and `abandonWorkflowRun` is typed as `RunStatus`. `pnpm typecheck` checks the public types strictly.
- `Lobster.run(input)` accepts input in the published types: under strict TypeScript it was typed `never[]`, so no input could be passed. The build now checks the public API types strictly (`tsconfig.api.json`). `ToolRunContext.mode` is gone (tool mode is always `tool`; the field was ignored).
- The tool envelope's and the SDK's types for a question now match what is sent: `requiresApproval` includes `initiatedBy`, `requiredApprover`, `requireDifferentApprover` and (now also sent) `onReject`, and both requests always carry their `type` and `resumeToken` (and an approval its `approvalId`), so hosts need not check for them. SDK stages get an empty, readable `ctx.stdin` (it had no stream methods).
- `getWait` (and `waits show`) returns an approval question whole: who may approve (`initiatedBy`, `requiredApprover`, `requireDifferentApprover`) and `onReject` were left out. `run --dry-run` shows `retry` on `switch` and `repeat` steps too.
- A command stopped by its own step's `timeout_ms`, or that returned and then stopped the run (an `approve` where a pipeline cannot pause, a spent cost limit), is recorded as failed, not as an unknown outcome: the run can be retried with `runs advance` and pruned by retention (it could be neither). `runs abandon` also closes a failed run whose commands were cut off (a `parallel` branch stopped by a sibling's failure), so retention can prune it.
- `runs advance` on a failed run gives the failed step its whole `retry` budget and a fresh `timeout_ms` again, as documented (it got one attempt, and a step whose deadline had passed timed out at once). Messages about an interrupted, abandoned or unrepeatable step name it by its step ids (`deploy/attempt-2/activity`), not its encoded internal key.
- `lobster upgrade` checks the saved command state of old pauses inside pipelines and skips (and reports) one that is malformed, instead of converting it into a run that fails when resumed.
- A "no" typed at the terminal cancels the run, as `resume --approve no` does (it used to fail the run with "Not approved", and a question published earlier stayed open: its old token could still answer it and restart the failed run). When a step's attempt fails or a run fails, the questions it published are withdrawn, and a wait of a finished run is never answered. In human mode, `lobster run` reports a cancelled run on stderr with the reason and exits 1 (a deadline used to cancel silently with exit 0); results carry the reason as `reason`.
- The engine is reorganized into small modules, each with one job: the saved checkpoint format (`engine/checkpoint.ts`, with each kind of node's state typed separately), the machine, one handler per kind of step behind a table, waits, asking, reporting, records, the step clock and the engine's errors. Behavior is unchanged except: an approval wait shown by `runs show` and `waits show` includes who may approve (`initiatedBy`, `requiredApprover`, `requireDifferentApprover`); the internal `_on…` callbacks of the run context are grouped under `ctx.hooks`; SDK stages are registered as commands with a name and help; and `upgrade.ts` and the retry policy moved (to `engine/` and `workflows/`).
- The SDK's `exec`, `approve`, `stateGet`/`stateSet` and `diffLast` stages run the built-in commands instead of copies of them, so they behave as those commands do in a pipeline (and check host authority before acting). Differences from before: `approve({ preview: false })` no longer drops the items for the stages after the approval (the request always carries them; `preview: true` adds a text preview of the first `limit`); `exec(..., { json: false })` yields one item per output line instead of the whole output as one string; `exec` with JSON and no output yields `null` instead of nothing; `exec` errors read like the command's (`exec failed (7): ...`, `exec command not found: ...`); `exec` gains a `stdin` option. Each stage carries its command's meta, so a resumed run treats it as it treats the command. Custom stages no longer get `ctx.stateDir` (`ctx.env.LOBSTER_STATE_DIR` holds it).
- The source is built with TypeScript's strict checks (`strict`, `noImplicitAny`), so the published type declarations name the SDK's stage, option and result types instead of `any`. Behavior is unchanged.
- One option parser for every CLI command: `--flag value` and `--flag=value` work everywhere, and a missing value, an unknown flag or a non-number where a number belongs (`runs list --limit abc`, `history show <id> x`) is a usage error with exit code 2 instead of being ignored or becoming NaN. Output formats are unchanged.
- Fixes from a review of this release's engine, loader and SDK work:
  - A for_each running items at once saves each item's output and its progress in the same save (they could be split across two saves, and a crash between them made the loop fail for good, or run an item again), and keeps how far it may run ahead bounded.
  - In conditions, a backslash in a quoted string is kept unless it escapes a quote or a backslash, so `matches "^\d+$"` means digits (it used to mean the letter d).
  - The steps inside a skipped `switch`, `repeat` or `parallel` count as skipped, so later conditions can read them (they failed with "Unknown step reference"); dry-run plans them the same way.
  - A `switch` with `retry` cannot contain approvals, input, sleeps or waits, like loops; `pause_ms`, `batch_size`, `item_var` and `index_var` are refused outside `for_each`; `pause_ms` and retry delays are capped like `timeout_ms`.
  - A failed run's envelope names that run, never an earlier run that failed with the same error object.
  - An SDK token from an older version is marked used only together with the run it becomes, after everything that could refuse it: a refusal (too few stages) no longer uses it up, and two resumes at once no longer get a spurious refusal. An older SDK pause not yet imported asks for `lobster upgrade`.
  - CLI usage mistakes in `signal`, `runs advance` and `runs abandon` exit 2 like the others; read-only commands work on a database made before records existed.
  - `llm.invoke` reported a live answer through an injected adapter as `cached: true`.
- Add `concurrency: N` to `for_each`: up to N items run at once, with outputs in item order. A failed item stops new items from starting, lets running ones finish, then fails the loop; a retry runs only the items that did not finish. Such a loop cannot contain approvals, input, sleeps or waits, or use `pause_ms`. Forty 50 ms items take 0.4 s at `concurrency: 8` instead of 3 s.
- Saves no longer grow with a run: a `for_each` loop's items and each item's output, and any step output over 1 KB, are kept beside the checkpoint as records written once, in the same transaction as the save that first needs them. A loop's saves used to rewrite every item and every finished output, so time and bytes grew with the square of its length (3,200 items wrote 630 MB and took 49 s; 8,000 items now take under 6 s). Records go when a run completes or is cancelled, stay with a failed run for its retry, and are included in `storage export`.
- `lobster runs advance --due` advances up to 4 due runs at once instead of one after another, so a slow run no longer delays the others; `--concurrency N` (`advanceDueRuns({ concurrency })`) changes it, and `--concurrency 1` restores the old behaviour. Each run keeps its own lease.
- A stop (Ctrl-C, a host abort, a lost lease) between a step being marked started and its command starting no longer leaves the run blocked: the step goes back to ready, since nothing ran. Shell steps count as started only once their process is spawned.
- Conditions nested more than 64 levels deep, or with a tree more than 256 levels deep (a very long `&&` chain), are refused with a message instead of overflowing the stack.
- Workflow files: `steps:` on a step other than `for_each` or `repeat` is refused (it used to crash with a TypeError when the run started); a NUL character in a `workflow` or `cwd` path is refused; a file that is not valid YAML or JSON says so, with its path.
- The CLI reports an error as one line instead of a stack trace (`LOBSTER_DEBUG=1` shows it): exit code 2 for a command line it does not understand, 1 otherwise. `lobster runs show` and `waits show` of an unknown ID fail with "not found" instead of printing `null`.
- Add the testing campaign (`pnpm test:campaign`, nightly in CI): randomized workflows run with and without interruptions, process chaos (SIGKILL, SIGSTOP past the lease, wrong clocks, a locked database), fuzzing of conditions, workflow files, pipelines and the CLI, and load and soak tests.
- Document recipes for deciding with a classifier (and asking a person when it is unsure), reminding an approver, waiting for whichever outcome comes first, and undoing earlier steps when a later one fails.
- Loops can pause: approvals, input, sleeps, waits, switches and child workflows may be steps of a `for_each`. A question inside a loop is asked once per item. A loop with `retry` cannot contain them, since a retry would ask again; that is refused when the file loads.
- Add `repeat` steps: `repeat: { until: <condition>, max: N }` runs its steps in rounds until the condition holds after one (for polling: check, sleep, check again). `max` is required; reaching it fails the step, or ends it with `on_max: continue`. Later steps see the last round's results and `$step.rounds`.
- Add `on_reject: continue` to approvals: a "no" completes the step with `approved: false` instead of cancelling the run, so a loop can skip one item. Identity rules apply to such a rejection too.
- A step's `timeout_ms` no longer counts the time a run spends paused inside it (a sleep, a wait or a question in a loop or a switch): enclosing steps get a fresh budget when the run continues. Before, a pause longer than an enclosing step's timeout failed that step on resume, except for answered questions.
- Split the README into a one-page guide (what Lobster is, five ideas, a first workflow, tool mode, operating runs) and a full reference in `docs/reference.md`, which keeps every section of the old README, grouped by topic. The package now ships the reference.
- Add `switch` steps: the first case whose `when` holds runs its steps (any kind of step, approvals and nested switches included), or `else`. The choice is saved, `$switch.json` is the output of the case that ran, `$switch.case` says which, and steps of other cases count as skipped. A switch with no matching case and no `else` fails.
- Conditions gain `in`, `contains` (list membership or substring), `matches` (a quoted regular expression) and list literals such as `[refund, spam]`. Every syntax error gives a character position.
- Conditions are checked further when the file loads: a condition that reads a step that does not run before it, or a literal operand that fails on every run (`$n.json.count > "high"`), is refused before any step runs. Before, a reference to an unknown step failed only when the condition was evaluated.
- Parse `when:` and `condition:` into a syntax tree once, then evaluate the tree, instead of evaluating while parsing. Conditions decide exactly as before (checked against the previous evaluator on a million generated conditions). Syntax errors now say what is wrong, for example "Unsupported condition: $a.json.ok = 1 (unexpected "=" at character 12)", and dry-run no longer mistakes `$step.field` inside a quoted string for a reference.
- Validate JSON Schemas with TypeBox's checker instead of Ajv, so Lobster no longer generates code at runtime and runs with code generation from strings disabled. Schemas are still read as draft-07 with `format` unchecked. Error messages keep the "<path> <message>" shape with some wording changes (for example "must have required properties a, b", "/extra is not allowed"). `llm.invoke` no longer fails when two output schemas share an `$id`. `withSchemaCompiler` is exported from `@clawdbot/lobster/core` for hosts that bring their own validator.
- Keep all state in one SQLite database (`lobster.sqlite`) in the state directory, and save workflow-file progress so interrupted runs can be continued with `lobster runs advance`. Requires the same runtime as OpenClaw: Node >=24.16.0 <25 or >=26.1.0.
- Add `lobster upgrade`, a one-off import of state saved by older versions: paused workflows and pipelines become waiting runs, and approval IDs, `state.set` values and paused SDK steps are imported. Existing resume tokens and approval IDs keep working. Until it runs, resuming such state fails with `upgrade_required`.
- Run standalone pipelines (`lobster '...'`, `runToolRequest({ pipeline })`) and SDK pipelines on the same engine as workflow files. Every pipeline is a recorded run (kind `pipeline` or `sdk`) that pauses, resumes and recovers like a workflow, and each resume token or approval ID resumes once. The whole pipeline is checked (command names and flags) before its first stage runs. History shows the pipeline's own step above its stages.
- In human mode without a terminal, a pipeline that reaches `approve` or `ask` now pauses and prints how to answer it (status, request and resume token), as workflow files do, instead of printing the request as output with no way to resume.
- An answer, once accepted, stands: if the run stops or fails afterwards, the question is not asked again and the run continues with `lobster runs advance`; a failed resume reports the run in its envelope (`runId`). Pipelines used to put the question back in some of these cases.
- SDK runs are resumed only by an instance with the same stages; add `Lobster.advance(runId)` for SDK runs that stopped or failed. `lobster runs advance` refuses SDK runs and `--due` skips them. SDK tokens resume once; tokens from older versions are honoured once, then refused.
- Retry a failed run from the step that failed with `lobster runs advance <runId>` (core `advanceWorkflowRun`, SDK `Lobster.advance`). Completed steps keep their results; a failed step that reported dispatch of a command that may not be repeated is refused. Failed runs keep their step records until retention deletes them.
- An answer for an outdated wait revision fails with `wait_conflict` and leaves the run free to answer at once, instead of locking it until its lease expired. Resume errors for an unknown or used token now read "Resume state not found" for pipelines and workflows alike.
- A run started by a host without an abort signal stops its child processes on Ctrl-C, as the SDK and pipelines did before.
- Workflow loops save their progress after every iteration, so very large loops run slower than before.
- Report runs stopped while a command was running as `blocked`, and add `lobster runs abandon <runId>` to stop them for good.
- Delete finished runs (completed, failed or cancelled) 30 days after they last changed, at most once a day when the store is opened for writing; set `LOBSTER_RUN_RETENTION_DAYS` (or `retentionDays` when opening a store) to change this, `0` keeps them forever. Waiting and blocked runs are never deleted.
- Update Node.js types to 24.19.2 to match the new runtime floor.
- Reject unknown keys in workflow files instead of ignoring them, suggesting the intended key for likely typos. A misspelled `when:` previously made its step run unconditionally.
- Fail a condition that orders anything other than numbers (strings, booleans, `null`, missing values) instead of evaluating it to false. `&&` and `||` now skip their right side when the left side decides the result, and a missing field equals the literal `null`, so guards like `$x.json.v != null && $x.json.v > 1` work. Conditions are checked for syntax when the workflow loads, and dry-run only checks the syntax of conditions on step output it does not have.
- Reject an `approval:` that is not `true`/`false`, a non-blank prompt or an object, and an `approval.prompt`/`preview` that is not a string or `approval.items` that is not a list. Such a value used to drop the gate, so the step ran without asking anyone.

- Validate `timeout_ms`, `retry`, `on_error` and `when` of `for_each` sub-steps like those of any other step, and reject any `approval:` or `input:` key in a sub-step. A quoted `timeout_ms: "5000"` inside a loop made the step time out at once.
- Refuse an approval or input gate inside a sub-workflow before its command runs; the command used to run and only then fail the run.
- Dry-run no longer lists a step as skipped when its condition reads an earlier step's output; the step is planned with its condition marked as unknown at plan time.
- Group commands into packs (`stdlib`, `openclaw`, `google`, `github`) and give every command a declared contract (`defineCommand`): description, flag schema, side-effect labels and whether it is `repeatable`. - Reject a flag a command does not declare, suggesting the intended flag for likely typos, instead of ignoring it.

Only `openclaw.agent` was covered before, so a crash right after `gog.gmail.send` sent could send again.
